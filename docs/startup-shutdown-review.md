# 启动、隐藏、关窗与退出评估

## 当前优化结果

本轮已把本地备份时间恢复、外部镜像时间扫描与启动备份移到**首个窗口首帧之后**。
本地时间恢复和启动备份在同一后台 worker 顺序执行，外部扫描单独运行；
周期备份如果先于后台初始化到达，也会先恢复历史时间再判断间隔，不额外创建一份备份。
旧扫描不能覆盖刚完成的备份/镜像，也不能在退出后发布状态。首次 Markdown 分块复用同一份行切片，少一次全文 `Split`。

| 场景（软件渲染） | 调整前 | 调整后 |
|---|---:|---:|
| 镜像状态扫描调用注入 3 秒等待，启动中位数，各 3 次 | **3,638ms** | **519ms** |
| 普通本地笔记启动，后测 5 次 | 原基线 669ms | **527ms**（487–1,208ms） |
| 1.20MB 多段落启动，后测 5 次 | 原基线 698ms | **609ms**（603–624ms） |
| 1.20MB 首次 Markdown 块缓存分配，5 次中位数 | 66.59MB | **65.30MB** |

3 秒是探针在状态扫描调用内注入的等待，不是真实失联网络卷测试；调整后的 3 个样本都在扫描未完成时
进行了模拟编辑、最终保存并成功退出，全部标签正文一致。阶段日志确认扫描在首帧后才开始。
普通本地前后测不是交替采样，受频率/系统负载影响，**不把 669→527ms 全部归因为本次改动**。
Markdown 微基准时间为 45.48→44.44ms，差异很小；确定的收益是少一次切行分配，未消除行内解析。

MyGo 仍固定 `v0.5.1`，没有修改系统/用户 GPU 配置，也没有替换已安装应用。
只读核对 `v0.5.5` 源码，基础 Metal `makePipelines` 仍同步创建；没有证据证明单纯升级即可解决下述长尾。
要进一步改善默认 GPU 首帧，需要在 MyGo 层实现/验证基础管线后台准备、缓存或首帧降级策略；
应用层定时器不能抢占已经阻塞的主线程。软件渲染可以绕开这条路径，但改变长期 CPU/功耗特征，
本轮保留现有渲染策略。

新增交错回归先验证失败、修正后通过；gofmt、Go vet、MyGo vet、全量普通测试、全量 race、
架构检查与原生 Dock 生命周期回归均通过。一次 `make check` 因工具 60 秒限制在 race 阶段被中断，
随后单独完成 `make race` 和 `make arch-check`；不把中断日志算作完整命令通过。

## 初次评估基线（启动优化前）

普通笔记的软件渲染启动中位数约 **0.67 秒**，可见窗口直接退出约 **83ms**，
点击 × 隐藏约 **38ms**。本地最终保存通常不到 1ms，没有发现普通笔记退出被保存逻辑长时间卡住。

**默认 Metal 首帧存在明显长尾，不能判定启动稳定达标。**
显式 `MYGO_GPU=1` 的首个样本在 15 秒内没有完成首帧；随后不设置 GPU 环境变量的默认路径，
一次为 **12.88 秒**，接着三个新进程为 **1.95 / 0.94 / 0.92 秒**。
超时线程采样落在主线程等待 Metal 渲染管线编译，说明图形初始化能够阻塞首窗；
后续变快说明该问题受运行环境/缓存状态影响，不代表每次启动都会慢，也不表示已经修复。

另一项明确瓶颈是 **5,000 行表格的主线程布局与窗口处理**：即使数据仅约 50KB，
首帧后立即退出中位数也达到 **538ms**，最终笔记写入却只有 **0.90ms**。

## 方法与范围

- 同一台 Intel i9-9880H Mac、darwin/amd64、macOS 26.7.1、MyGo v0.5.1；当前工作区源码。
- `go build -overlay` 在临时目录构建独立 `.app`，执行其可执行文件；编译时间不计入启动。
  不包含 Finder、LaunchServices、Dock 点击派发和已安装版签名检查的完整开销。
- 应用数据、偏好、日志和应用缓存都指向临时目录；没有读取或修改日常笔记和已安装应用。
  合成偏好启用启动备份、800ms 自动保存，未配置外部镜像/Git；不是首次安装向导路径。
- 启动从父进程创建子进程前计时，到 MyGo `OnReadyToShow`（首帧绘制结束）为止，
  再投递主线程空回调确认事件循环可响应。该指标不是完整键盘/IME 编辑验证。
- 每个普通场景 5 次独立进程，报告全部样本中位数；未清空系统/Metal 缓存，
  不将第一次样本称为重启后的冷启动。默认 GPU 后续组只有 3 次，另有 1 次 12.88 秒样本。
- 隐藏/显示/关闭通过探针投递到主线程，调用相同窗口 API；不包含真实鼠标或快捷键事件投递。
  退出从后台调用 `App.Quit()` 前计时，到父进程观察退出为止，包含主线程排队、关窗、保存与进程收尾。
  父进程轮询存在几毫秒观测误差。
- 读日志、阶段打点和临时构建路径也有测量开销；不同批次受到系统负载/频率影响，
  小差异不解释成规模增大反而更快，也不作为跨机器保证。

当前源码启动顺序为：目录迁移/装配 → 读取笔记并解析当前文档 → 偏好 → 原生事件循环 →
菜单、托盘和热键 → 建窗 → 首帧/图形初始化 → 后台备份/镜像状态恢复及启动备份。
初次评估时，两项目录状态扫描在菜单/建窗之前同步执行；下方原始基线保留该实现的结果。
现有“应用就绪”日志在建窗后输出，**早于首帧**，不能用这条日志代表用户已经看到界面。

## 软件渲染基线

以下均为 `MYGO_GPU=0`，用于隔离 Metal 初始化；每行 5 次。退出在首帧后直接发起。

| 合成输入 | 进程创建到首帧，中位数 | 可见窗口退出到进程结束，中位数 | 最终笔记保存，中位数 |
|---|---:|---:|---:|
| 普通 Markdown，5,760 字节 | **669ms** | **83ms** | 0.70ms |
| 多段落，实际 UTF-8 1.20MB | 698ms | 95ms | 8.56ms |
| 当前短便签 + 后台标签 10MiB | 668ms | 127ms | 34.25ms |
| 单段 100,000 个 ASCII 字符 | 723ms | 81ms | 0.81ms |
| 5,000 行双列表格，50,016 字节 | **808ms** | **538ms** | 0.90ms |
| 源码模式，8,000 行 Go 代码 | 663ms | 81ms | 1.42ms |

普通笔记这一组范围为 652–1,343ms；其他批次新构建的第一个进程还出现过 1.6–2.9 秒，
不能只用中位数声称任何一次启动都小于 1 秒。表格等待 2 秒后再退出仍为 247–319ms，
并非只有启动时立即退出才出现延迟；该批次负载与前一批不同，不据此精确量化等待的收益。

笔记载入阶段包含读取、JSON 解析与当前 Markdown 分块/同步：普通笔记中位数 0.79ms，
1.20MB 多段落约 77.5ms，后台标签 10MiB 约 39.1ms。
大量当前段落的处理可以比更大的非当前纯文本标签更贵，总字节数不是唯一因素。
10MiB 最终保存约 33–35ms，主要是整个快照 JSON 编码和原子写入；仍是同步退出成本。

## ×、⌘W 和真正退出

当前顶栏 × 调用 `Window.Hide`，保留进程、文档和原生窗口；⌘W 调用 `Window.Close`，
关闭主窗口但应用仍驻留。只有 ⌘Q、菜单退出等才执行 `OnWillQuit → finishQuit` 最终保存并结束进程。

在首帧后等待 1 秒，按“隐藏 → 显示/聚焦 → 关窗 → 退出”顺序测量，各 5 次：

| 操作 | 普通笔记，中位数（范围） | 5,000 行表格，中位数（范围） |
|---|---:|---:|
| 发出隐藏请求到 `Hide` 返回 | **38ms（35–42）** | 45ms（39–59） |
| 发出显示请求到 `Show/Focus` 返回 | 21ms（18–33） | 129ms（120–143） |
| 发出关闭请求到 `Close` 返回 | **26ms（10–29）** | **266ms（240–277）** |
| 窗口已关闭后，退出到进程结束 | **17ms（11–17）** | 49ms（37–53） |

请求耗时包含主线程排队；`Show/Focus` 返回不代表恢复后的首帧已呈现，不能把 21ms 当作 Dock 点击全链路延迟。
普通笔记“先隐藏再退出”另测 5 次，退出为 **24–33ms**，包含仍未自动保存的模拟编辑。
之前的真实 Dock 回归已覆盖隐藏复用和关闭重建，见[窗口与性能报告](performance-review.md)。

表格 `Close` 自身中位数约 144ms，而发出请求到返回约 266ms，说明排队和原生窗口处理都有成本；
退出最终写盘不足 1ms。进一步定位各层比例还需要布局/绘制及 AppKit 关闭路径采样，
不能仅凭这组阶段计时把全部延迟归于某一个函数。

## 退出时的数据保存

源码退出流程先停止接受新请求、取消防抖计时器，再等待在途笔记写入，最后写当前快照；
随后等待偏好最终保存。不等待后台镜像/Git，不会因为远端 push 的返回而一直无法退出。
但慢磁盘、正在进行的本地写入、偏好保存仍会增加退出时间。

模拟主线程编辑后，走正常 `scheduleSave()`，在 800ms 防抖到期前立即退出：

- 普通笔记 5 次：59–72ms，最终正文与模拟编辑完全一致。
- 大表格 5 次：308–356ms，最终正文与模拟编辑完全一致。
- 普通笔记编辑后先隐藏再退出 5 次：24–33ms，最终正文一致。
- 对最终笔记写入额外注入 150ms 等待，5 次退出为 **234–242ms**，其中最终笔记保存 **151.1ms**；正文一致。

以上验证的是正常最终写入及待保存编辑，不是磁盘写入失败注入，也不代表真实输入/IME 回归。
慢写结果说明退出确实等待最终落盘，没有为了缩短退出而丢弃最后改动。
所有成功退出的样本都校验了全部标签正文；原有最终保存失败/重试和写保护测试仍由项目测试负责。

## 优先级与后续建议

1. **P1：默认 Metal 首帧长尾。** 保留驱动采样与 MyGo 调用链，核查渲染管线缓存、初始化时机和可行的降级策略。
   同步编译已经阻塞主线程，不能简单加一个同线程 timer 就认为可以超时退出。
   修改渲染策略前需分别复测新构建首进程、后续进程及真实安装 bundle。
2. **P1：大表格等大块主线程工作量。** 当前外层列表虚拟化不能约束块内 cell；进一步做块内虚拟化，
   覆盖选择、编辑、IME 和滚动。这个问题既影响编辑，也会拖慢启动/关闭响应。
3. **P2：外部卷与特殊启动路径的验证。** 本轮目录扫描已移到首帧后的后台任务，
   通过注入 3 秒等待验证首帧和退出不再等待镜像状态扫描；仍未测真实失联 SMB/NFS、
   大量历史备份、升级迁移或手写字体首次注册。
4. **P2：大数据退出成本。** 当前 10MiB 本地保存约 34ms，尚可接受；更大数据、慢盘和在途保存需单独量测。
   如后续减少无改动重复写入，必须以修订状态和保存成功确认保证最终一致性。

原始基线和长尾采样完整保留；当前新增优化的范围、回归及检查结果见本文开头。
尚未替换正在运行的安装版，不能把临时测试 bundle 的变化当作安装版已经生效。


输出文件使用追加模式，复跑应选择新文件，避免混合历史样本。`1m-paragraphs` 是场景标识，
实际长度为 1,200,000 UTF-8 字节，以记录中的 `textBytes` 为准。
一次旧探针非原子发布命令导致读到空字符串，两个控制命令超时；它们不是应用挂起，
已保留在 `native-lifecycle-close-harness-race.jsonl` 并从应用统计排除。
修正为原子发布后该场景 10/10 成功。GPU 的 `responsive` 超时发生在启动阶段，
不能归到该命令发布问题；其主线程 Metal 等待栈保留在原始记录内。
